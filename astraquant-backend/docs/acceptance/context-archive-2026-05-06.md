## 2. 总体推进原则

后续工作采用“逐 Sprint 完善”的方式推进，而不是重构。

核心原则：

1. 不推翻已经完成的系统架构。
2. 不为了贴合早期设计文档而破坏后续 Sprint 已经演进出的能力。
3. 每个 Sprint 以原始设计为需求来源，以当前代码为实现事实，以真实平台可用为最终验收标准。
4. 每个 Sprint 都必须补齐技术方案、前后端对接、测试用例和验收记录。
5. 每个 Sprint 的完善都要能被测试工程师验证，而不是只停留在开发自测。
6. 质量由测试工程师通过系统化测试保障，开发负责修复缺口和补齐可测性。

一句话：

```text
按 Sprint 逐个完善，让每个模块真正可用、可测、可验收。
```

## 3. 不是重构，而是验收型完善

后续工作不应被定义为重构。

允许做：

- 修复缺陷。
- 补齐遗漏接口。
- 补齐测试。
- 补齐前后端字段契约。
- 补齐错误码。
- 补齐权限校验。
- 补齐审计与告警。
- 补齐数据库持久化。
- 补齐 Docker Compose / 环境变量。
- 补齐真实链路验收脚本。

不主动做：

- 大规模改目录结构。
- 推翻已有服务边界。
- 删除后续 Sprint 依赖的能力。
- 为早期文档回退 RBAC、Gateway 或统一响应等已经演进出的系统能力。
- 无验收价值的抽象重构。

## 4. 每个 Sprint 的固定验收产物

每个 Sprint 都要沉淀一套验收包：

1. 当前实现差异分析
   - 原始设计是什么。
   - 当前实现是什么。
   - 差异在哪里。
   - 哪些差异是合理演进。
   - 哪些差异是缺口。

2. 验收技术方案
   - 服务职责。
   - 数据库。
   - API。
   - 权限。
   - 事件。
   - 缓存。
   - 审计。
   - 告警。
   - 部署与环境变量。

3. 前后端对接文档
   - 页面入口。
   - API 路径。
   - 请求参数。
   - 响应结构。
   - 状态流转。
   - 错误码。
   - 权限要求。
   - 前端展示建议。

4. 测试用例清单
   - 单元测试。
   - API 测试。
   - 权限测试。
   - 数据库测试。
   - 事件测试。
   - 前端页面测试。
   - 端到端测试。
   - 异常路径测试。

5. 验收执行记录
   - 已通过项。
   - 未覆盖项。
   - 发现的问题。
   - 修复记录。
   - 剩余风险。
   - 是否允许进入下一个 Sprint 验收。

## 5. 测试工程师质量保障职责

测试工程师应按 Sprint 维度主导质量验收。

测试工程师重点负责：

1. 将设计文档转换为可执行测试用例。
2. 维护 Sprint 验收矩阵。
3. 验证 API 与前端契约。
4. 验证权限边界。
5. 验证异常路径。
6. 验证数据库落库与迁移。
7. 验证事件发布与消费。
8. 验证审计与告警。
9. 验证 Docker Compose / 本地环境启动。
10. 输出验收报告。

开发工程师重点负责：

1. 修复验收发现的问题。
2. 补齐缺失 API 或字段。
3. 补齐测试辅助能力。
4. 补齐文档与实现一致性。
5. 保证每次修复都有自动化测试覆盖。

## 6. 推荐推进顺序

从 Sprint 1 开始，按顺序推进：

```text
Sprint 1 → Sprint 2 → Sprint 3 → ... → Sprint 20
```

原因：

- 后续 Sprint 依赖前面 Sprint。
- Auth、Gateway、统一响应、trace_id、权限是全系统基础。
- 先把基础验收清楚，可以减少后续模块反复返工。

## 7. Sprint 1 当前重要上下文

用户提供的 Sprint 1 V1.1 文档定位为：

```text
单用户 / 管理员权限模式
登录成功 = 拥有全部系统操作权限
```

但当前代码经过后续 Sprint 演进，实际系统已经更接近：

```text
RBAC 权限模型 + FastAPI API Gateway + 多服务权限控制
```

后续验收不应强行回退到早期单用户形态，而应采用：

```text
原始设计作为需求来源
当前实现作为事实基础
最终平台可用作为验收目标
```

Sprint 1 验收时重点确认：

- 登录是否可用。
- Token 是否可用。
- Gateway 是否可代理。
- 当前用户是否可识别。
- 权限扩展是否不影响管理员使用。
- 前端登录与主框架是否可用。
- 基础依赖是否可启动。
